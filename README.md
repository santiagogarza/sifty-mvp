# Sifty

Calm, AI-first productivity. Capture instantly. Sifty organizes the rest.

> **Branches:** `production` is the live product (Vercel deploys from it);
> `master` is the fresh pre-demo baseline; `demo-done` and `dragging-bug`
> are demo branches. Read [`BRANCHES.md`](./BRANCHES.md) before opening a PR.

## Run

```bash
pnpm install
cp .env.example .env.local       # then fill in values
pnpm dev
```

Visit http://localhost:3000 — it redirects to `/today`.

### Quickest local setup (no auth, no DB, no AI keys)

```bash
SIFTY_DISABLE_AUTH=1 SIFTY_AI_OFFLINE=1 pnpm dev
```

`SIFTY_AI_OFFLINE=1` routes triage and agent briefs through the
deterministic offline heuristic so the full loop works without a provider
key. Without it, AI routes fail clearly (503 `no_ai_key`).

### Demo workspace

```bash
SIFTY_DISABLE_AUTH=1 SIFTY_AI_OFFLINE=1 SIFTY_DEMO_SEED=1 pnpm dev
```

`SIFTY_DEMO_SEED=1` populates every new account (or the auth-bypass user)
with a fully-triaged workspace: a dozen tasks across Today/Inbox/Focus/
Waiting on/Someday/Done — labeled, prioritized, with subtasks, rationale,
confidence, one clarifying question, and one prepared agent brief — plus
pinned memories. Seeding is first-run only: an account with any existing
task or memory is never touched. It works with real sign-up too (each new
account gets the demo set), and with or without a database.

## Design philosophy

Sifty optimises three things, in this order:

1. **Calm.** The app should never shout. Empty states are quiet, motion is
   subtle, the type stack is generous. The single warm accent ("ember") is
   reserved for true urgency; "mist" is the AI hue and stays quiet.
2. **Instant capture.** The capture dialog is reachable from anywhere
   (`C` shortcut), opens with the textarea focused, and submits with
   `⌘↵`. The task is created synchronously and AI enrichment happens in
   the background — capture never blocks.
3. **AI you can argue with.** Every AI-derived field is editable, and every
   user edit is recorded so re-triage will not overwrite it. Rationale and
   confidence are visible in the detail sheet so you can disagree on
   evidence, not vibes.

## Sync architecture

The Zustand store is the optimistic source of truth for the UI; Postgres is
the durable source of truth across devices.

- Every mutation (task capture/edit/delete, labels, memories) pushes to the
  API in the background: creates and deletes immediately, field edits
  debounced 400 ms, always full-entity last-writer-wins, per-entity ordered.
- A localStorage ledger marks entities dirty before each push (with
  tombstones for deletes). Pushes that never land — tab closed, offline —
  replay on the next mount.
- On mount the client pulls the server snapshot and reconciles: dirty-local
  wins, clean rows follow the server, tombstones are honored, and an
  account switch on a shared browser resets the local cache instead of
  leaking the previous user's workspace.
- Sifting runs server-side in the `siftTask` workflow (see "Background
  jobs"): `POST /api/tasks` enqueues it, every stage writes the task with
  `editedFields` protection, and the browser only polls `GET /api/tasks/:id`
  to show "Enriching → Prioritizing → Triaging → Breaking down → Planning".
  Closing the tab changes nothing. Tasks still `pending`/`running` after a
  pull are watched again (bounded) on the next load.

## Background jobs (Vercel Workflow)

Durable, multi-step work runs on [Vercel Workflow](https://vercel.com/docs/workflows)
(`workflow` v5, on Vercel Queues). Workflow and step functions live in
`lib/workflows/`; routes enqueue through `startWorkflow()` in
`lib/workflows/dispatch.ts`, the single seam tests swap out.

How it is wired:

- `next.config.ts` is wrapped with `withWorkflow()`, which compiles the
  `"use workflow"` / `"use step"` directives and generates the queue-triggered
  flow route under `app/.well-known/workflow/` at build time (gitignored).
- **On Vercel** the managed "Vercel World" is selected from
  `VERCEL_DEPLOYMENT_ID`: storage, queues, and OIDC auth are provisioned by
  the platform, runs are pinned to the deployment that started them, and
  every run shows up under the project's **Workflows** tab. Two project
  settings must stay on: *Enable access to System Environment Variables*
  and Fluid Compute (both default on for new projects). Workflow is
  available on the Hobby plan with an included monthly allotment of events.
- **Locally** (`pnpm dev`, `pnpm start`, Playwright) the bundled Local World
  runs inside the Next.js process and stores runs as JSON under
  `.next/workflow-data/`. No extra service, no env var. `pnpm dev` uses
  webpack: Turbopack on Next 15.1 cannot bundle the Workflow runtime
  (`assert/strict` resolution in `@vercel/queue`), and `pnpm dev:turbo`
  stays available for UI-only work that never enqueues.
- `SIFTY_AI_OFFLINE=1` keeps every step deterministic (same heuristic as the
  synchronous triage), so the full pipeline runs in CI and demos without a
  provider key.

Operating it:

```bash
pnpm workflow:web               # local dashboard: runs, steps, inputs/outputs
pnpm workflow:runs              # list local runs in the terminal
npx workflow inspect runs --backend vercel --project sifty-app --team santiagogarzas-projects
```

Smoke test a deployment as the creator: `POST /api/admin/workflow-ping`
(button at `/admin/costs`) starts a one-step workflow and waits for it.
`completed` means the queue trigger, flow route, and storage all work.

Concurrency: Workflow has no built-in per-user concurrency key, so
`lib/workflows/user-lock.ts` turns hook tokens into slots: a run claims one
of N `scope:userId:slot` tokens before its first step and holds it until the
run ends; when all slots are busy it suspends on the owners' results.

Cost accounting: every step writes an `ai_runs` row with `stage`,
`prompt_version`, `sift_id`, and `workflow_run_id`. Caps count sifts, not
steps (`sift_id IS NULL OR stage = 'sift'`). The creator-only `/admin/costs`
page rolls the table up by day, stage, model, and account.

### The `siftTask` pipeline

`lib/workflows/sift-task.ts` runs five steps on every new capture (and on
"re-sift now"), each backed by `lib/ai/sift/`:

| Stage | Model class | Writes | Prompt version |
| --- | --- | --- | --- |
| `enrich` | fast | title, description, next action, due hint, labels | `enrich.v1` |
| `prioritize` | fast | urgency, importance, effort, rationale — **list-aware**: the prompt sees the user's other open tasks | `prioritize.v1` |
| `triage` | fast | routing (inbox task → `waiting` / `someday` only), delegation candidate, confidence, clarifying question + up to four tappable options | `triage.v3` |
| `subtasks` | fast | up to five subtasks when the work has distinct steps | `subtasks.v1` |
| `plan` | deep | `task.plan`: executor (`ai_agent` / `cursor_agent` / `person` / `self` / `none`), approach, connectors, readiness, blockers | `plan.v1` |

Rules that hold at every step:

- The step re-reads the task; if `task.siftId` changed (a re-sift) or the
  task is gone, the run stops. A re-sift never races an older run.
- `editedFields` are never overwritten; the patch is narrow, so a user edit
  that lands between steps survives.
- One `sift` accounting row is written when the sift is accepted (before
  `start()`), so the tier cap sees it immediately; a sift that fails to
  start or dies flips that row to `failed` and is not billed.
- Transient model errors retry (Workflow default, 3 retries); a missing
  key or a bad `AI_TRANSPORT` is fatal and surfaces as `aiStatus: failed`
  with a retryable message.
- With `SIFTY_AI_OFFLINE=1` (or `?offline=1` off production) every stage
  uses the deterministic heuristic through the same steps.

### Decisions (clarifying questions)

When `triage` is unsure it asks one question instead of guessing. The
pipeline still finishes — the task is `ready` with Sifty's best read — then
the run opens a `clarifying_question` row in `decisions`, registers a
Workflow hook under `decisions.resume_token`, releases its per-user slot,
and suspends with no compute for up to seven days.

- `/decisions` is the one inbox for everything waiting on the human
  (memory proposals in 2.4 and approvals in Phase 3 land in the same
  list). Answer with a tapped option or a line of text, or "Let Sifty
  decide". The badge in the sidebar (top bar on phones) is the open count.
- **Answer** → `POST /api/decisions/:id/answer` resolves the row once
  (compare-and-set; a second answer is `409`) and resumes the hook. The run
  folds the answer into the capture as an `Answer:` line and runs every
  stage again **inside the same sift** — one cap unit, and the second pass
  never asks another question. If no run is waiting (deploy, deadline), the
  answer is folded in here and a fresh sift is enqueued instead.
- **Dismiss** → the task is marked `siftedWithAssumptions` (shown in the
  sheet with a re-sift link) and the run ends.
- A re-sift or a delete expires the task's open questions and releases
  their runs; the 7-day deadline expires an ignored one.
- One-tap links (`lib/decisions/links.ts`): HS256 JWTs under
  `BETTER_AUTH_SECRET`, 24 h, scoped to one decision and one action, used
  by digests and pushes via `/api/decisions/link?token=`. `GET` never
  changes state (mail scanners and unfurlers fetch every URL): `open`
  redirects into the inbox, `answer` / `dismiss` show a one-button page
  that `POST`s the token back, and only the `POST` resolves. Single use
  follows from the decision's own state machine. The notifications worker
  reads `listOpen(userId)` from `lib/decisions/service.ts`.

### The `dailyPlan` workflow

`lib/workflows/daily-plan.ts` re-ranks Today and Focus against the user's
whole open list, once a night per account and on demand from **Re-plan
today** on the Today page (Pro and creator; `caps.dailyPlan`). Backed by
`lib/ai/plan/`:

- **Bounded reads.** Two queries (open tasks due within seven days, soonest
  first; the most recently touched open tasks) are merged and ranked
  deterministically; the top 60 go to the model, the rest are a count. A
  user with 500 tasks costs the same as one with ten. Tasks mid-sift are
  skipped — their own `prioritize` stage is about to score them.
- **One model call per run** (`dailyplan.v1`, stage `prioritize`,
  fast-class model), one `ai_runs` row that counts as one sift against the
  tier cap. The row is reserved before `start()` (so the next request's
  cap count already includes it) and completed with the model's usage by
  the decide step, so a retried step never bills twice. The model answers
  in aliases (`t1`, `t2`, …) that resolve only to the task ids the prompt
  was rendered with, so a hallucinated handle maps to nothing and a
  re-ranked list cannot redirect a decision.
- **Guards the model cannot skip** (`lib/ai/plan/apply.ts`): `editedFields`
  protection per field; a task due more than a day out is never pulled
  into Today (snoozes stay snoozed); at most eight score-driven promotions
  per run; deadline-forced tasks are in Today regardless.
- **Explainable.** Every applied change writes a `task_events` row
  (`plan.moved_in` / `plan.moved_out` / `plan.rescored`) with a message
  such as "Moved into Today: due tomorrow, deep work", and the same text
  becomes the task's `rationale`. The run's summary and moves are stored
  on `daily_plans` and shown on the Today page.
- **Scheduling.** `/api/cron/daily-plan` (daily, 04:00 UTC on Hobby) walks
  every account, skips free tiers, idle accounts, and anyone at their cap,
  then claims one `cron` plan per user and local day (partial unique index)
  before `start()`. Claims are atomic per user (advisory lock): at most one
  plan runs at a time, so two overlapping "Re-plan today" clicks start one
  workflow. The plan is for the user's local date — tomorrow when it is
  already past 18:00 there — in the zone saved with their notification
  preferences (UTC until they save one); the manual route takes the
  browser's zone.
- Offline (`SIFTY_AI_OFFLINE=1`) the deterministic variant applies the same
  rules the prompt describes, so the whole flow runs in CI and demos.

### Memory extraction

`lib/ai/memory/` proposes durable facts and preferences — "Ana =
accountant", "prefers mornings for deep work" — and asks before remembering
them. Backed by the Decisions inbox (`memory_proposal` decisions):

- **When it runs.** As a best-effort tail step of `siftTask` once the task
  is `ready` (never fails a sift), gated by a cheap regex prefilter
  (`prefilter.ts`) so mundane captures cost no model call; and as the
  one-step `memoryFromEdit` workflow when `PATCH /api/tasks/:id` reverses
  the sift on a signal field (urgency, importance, effort, due, delegation,
  labels) for the first time — once per task and sift, tracked by a
  `memory.extracted` task event.
- **One call, `memory.v1`** on the `memory` route (fast class). The prompt
  sees the capture, how Sifty organized it, the *pinned* memories (the same
  gate sift, plan, and brief apply; unpinned notes stay local and only
  dedupe), and the user's edit; it answers with at most three proposals (text, kind,
  quoted evidence, confidence) and is told that an empty list is the usual
  answer. The `ai_runs` row carries the task's `siftId`, so it is a detail
  row of that sift, never a billing unit.
- **Dedupe and negatives** (`propose.ts`). Proposals below 0.6 confidence
  or matching an existing memory (normalized text) are dropped. The sink
  then checks the user's past `memory_proposal` decisions in any status:
  an open row, a confirmed one, or a dismissed one all block the same idea,
  so a dismissal is the durable "don't ask again".
- **Confirm / dismiss.** In the inbox a proposal reads "Remember this?" with
  **Remember** (writes a pinned memory the next sift and the daily plan use)
  and **Not this** (resolves the row as `dismissed`; nothing is written).
- Offline, a regex variant (`offlineMemoryExtraction`) covers "Name, my
  role", first-person habits, and a lowered urgency on a recurring category.

## AI configuration

Triage runs through the [AI SDK](https://sdk.vercel.ai/) and validates
output against the `TriageOutput` Zod schema. The system prompt and
prompt builder are in `lib/ai/prompts.ts`.

The model registry (`lib/ai/models.ts`) keys models by canonical
`provider/model` slug and declares, per pipeline stage (`enrich`,
`prioritize`, `triage`, `subtasks`, `plan`, `execute`, `digest`), a primary
model, an ordered fallback list, and list prices. Defaults: Claude Haiku 4.5
for the cheap stages, Claude Sonnet 4.5 for `plan`/`execute`, one OpenAI
fallback per stage. Settings → AI model is a *preference* (Recommended, Best
quality, Fastest, Prefer OpenAI) that remaps stages by class; the UI never
sees raw model ids.

`lib/ai/provider.ts` is the only module that imports a provider SDK.
`resolveProvider(stage)` returns an AI SDK model with the fallbacks baked
in for the configured `AI_TRANSPORT`: in `gateway` mode the fallback list
is passed to the Gateway as a routing option; in `direct` mode an
in-process wrapper fails over on retryable provider errors. Every
`ai_runs` row records `stage`, `transport`, the model that actually
answered, tokens, and `cost_cents` (fractional) priced from the registry,
so spend reporting works identically in both modes.

Pinned memories from `/memory` are passed into the prompt as `User
preferences` — adding a memory like "I avoid deep work after 4pm"
demonstrably influences how the model triages later evening tasks.

If the configured transport is missing its key, the route returns 503 with
`code: "no_ai_key"` (an invalid `AI_TRANSPORT` value gives `ai_misconfigured`).
The deterministic offline heuristic still works as an explicit debug
fallback via `/api/triage?offline=1` or `SIFTY_AI_OFFLINE=1` — useful for
keyless local dev, screenshots, and CI smoke runs.

"Prepare for agent" (`/api/agent-brief`) turns a task into a markdown
handoff brief — objective, context, steps, success criteria — stored on
the task and shown in the detail sheet with copy/regenerate. Same gates,
schema validation, and offline fallback as triage.

### Prompt evals

`pnpm eval` runs the golden capture set (`evals/golden/captures.json`, ~60
realistic captures across work, personal, vague, multi-task, and
adversarial inputs) through the five sift stages and checks, per stage,
schema validity, rubric properties (urgency/importance ranges, actionable
subtasks, clarifying question only below the confidence threshold, no
instruction-following from task text), and cost against the registry
prices. Offline (`SIFTY_AI_OFFLINE=1`) it is deterministic and runs on every
`production` PR; the "Evals (real models)" workflow runs it nightly through
the AI Gateway and weekly direct. Every prompt change bumps its
`promptVersion` and re-records `evals/baselines/` (`pnpm eval:update`); the
policy is in `lib/ai/prompts.ts`, the harness in `evals/README.md`.

## Billing

Tiers (`lib/entitlements/entitlements.ts`), lowest to highest; when several
facts apply the highest wins (`creator > comped > pro > trialing > free`):

| Tier | Who | Sifts/day | Execution budget | Connectors |
| --- | --- | --- | --- | --- |
| `free` | Everyone after the trial | 5 | — | no |
| `trialing` | New sign-ups, 30 days of Pro | 200 (fair use) | $10/mo | yes |
| `pro` | Paying via Stripe | 200 (fair use) | $10/mo | yes |
| `comped` | Pro granted by an invite code, no Stripe | 200 (fair use) | $10/mo | yes |
| `creator` | `CREATOR_EMAIL` | unlimited | unlimited | yes |

Capture, organize, sync, and reminders are free for every tier. The
`entitlements` row stores facts (trial window, `subscription_active`,
`comped_at`/`comped_until`); `deriveEntitlement()` resolves the effective
tier and its caps at read time, and `canRunAi()` gates on `caps.siftsPerDay`.
AI routes answer `402` with `code: "free_cap"` (upgrade path) or
`"fair_use_cap"` (Pro ceiling).

- Checkout: `/api/stripe/checkout` (POST `{ cadence: "monthly" | "yearly" }`)
  creates the Stripe customer if needed, then a Checkout Session with
  `allow_promotion_codes: true`. Discount/comp codes you create in the
  Stripe Dashboard are redeemable end-to-end.
- Portal: `/api/stripe/portal` (POST) opens the Stripe Billing Portal
  for active subscribers.
- Webhook: `/api/stripe/webhook` verifies the `Stripe-Signature` HMAC,
  deduplicates by `event.id` in the `stripe_events` table, then runs the
  pure reducer in `lib/billing/events.ts` against the user's
  entitlement. Creator entitlement is sticky.
- UI: `/settings/billing` shows tier, sifts used today, trial countdown,
  Upgrade (monthly/yearly), Manage subscription, and invite-code redemption.

### Invite codes

Invite codes grant `comped` (Pro without Stripe). Stripe promo codes stay for
percentage discounts at checkout; invite codes are for family, friends, and
anyone who should never enter a card.

```bash
pnpm invite:mint --months 12 --max 1 --expires 2027-06-30 --note "Ana"
pnpm invite:list
pnpm invite:revoke sifty-… [--cascade]   # --cascade also ends redeemers' comps
```

- Format: `sifty-` + 20 characters from an alphabet without 0/O/1/l/I
  (~117 bits). Only `sha256(INVITE_CODE_PEPPER + code)` is stored; the
  plaintext is printed once at mint time.
- `--months` omitted means forever; stacking a second timed code extends
  from the current comp end. `--max` is the redemption cap across users;
  each user can redeem a given code once.
- Redeem at `/redeem?code=sifty-…` (signed-out visitors go through sign-in
  or sign-up and land back on the code) or in Settings → Billing. The API,
  `POST /api/invites/redeem`, is rate-limited per user and per IP and
  checked with BotID.
- Requires `DATABASE_URL` and `INVITE_CODE_PEPPER`; both the CLI and the app
  must use the same pepper.

## Pre-deploy smoke checklist

Run through this on the preview URL before promoting to production:

- [ ] Sign-up flow lands a fresh user on `/today`.
- [ ] Capture creates a task instantly; triage status flips from
      `running` to `ready`; rationale + confidence are populated.
- [ ] Editing a triage field protects it on re-triage (toggle re-triage,
      observe the field doesn't change).
- [ ] Settings → AI model picker change is reflected in `meta.model` on
      the next triage run.
- [ ] `/settings/billing` shows the trial countdown.
- [ ] Stripe Checkout completes with `4242 4242 4242 4242` and a
      promo code; webhook activates the entitlement.
- [ ] Forging a webhook signature returns 400.
- [ ] Replaying the same `event.id` returns 200 + `deduped: true` with
      no duplicate DB writes.
- [ ] Free account past 5 sifts hits the AI route → 402 with
      `code: "free_cap"` and the upgrade message.
- [ ] Bursting `/api/triage` past the per-minute cap returns 429 with
      `Retry-After`.
- [ ] Sentry / logs receive a structured `reportError(...)` payload from
      a forced server failure.
- [ ] Capture a task, clear site data (or use a second browser), sign in
      again — the task and its enrichment come back from the server.
- [ ] Editing a task offline (dev tools → offline) and reloading once back
      online replays the edit (dirty ledger).

## Testing philosophy

Tests in this repo justify their maintenance cost. We have tests for:

- Pure boundary logic — Zod schemas, the entitlement matrix, the Stripe
  event reducer, prompt builder.
- Server route contracts — input validation, entitlement gating, error
  mapping, `ai_runs` persistence, rate-limit enforcement, webhook HMAC +
  idempotency.
- Cross-tenant tenancy invariants on the repo layer (no cross-user reads
  or writes).
- Auth — sign-up, email verification, sign-in gating on verification,
  password reset (with session revocation), magic link, per-session and
  all-other-sessions revocation, legacy bcrypt import; middleware gating
  protected and public routes. All against Better Auth's memory adapter and
  the console email outbox.
- One Playwright smoke per stage that exercises the happy path on the
  live server.

We do not test rendered output of every component, the deterministic
heuristic (it's a debug fallback, not a product feature), or LLM output
content (the schema parser is what we trust).

Pre-merge gate (also enforced in `.github/workflows/ci.yml`):

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```
